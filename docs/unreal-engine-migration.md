# Unreal Engine 迁移方案与可行性评估

## 结论

可行性：**高，约 8/10**。物理数据、天体定义、C17 数值核心、星历接口和尺度分层可以复用；Three.js 场景、GLSL 材质、DOM 标签与 CSS UI 不能直接搬入 Unreal，需要按 UE 的渲染和交互体系重建。

最稳妥的路线不是把网页“包装”进 UE，而是保留现有项目作为经过验证的行为原型，以数据契约为边界重建原生 UE 客户端。

## 可直接继承的部分

- `core/` C17 N 体代码：封装为 UE C++ 模块，或先编译为静态库并提供窄 C ABI。内部继续使用 SI 单位和 `double`。
- 天体 ID、质量、半径、父子关系、星历时刻和速度倍率等数据模型。
- Astronomy Engine 的结果与 JPL 对照用例可作为迁移验收基准；生产 UE 版本可换成 C/C++ 星历库，但输出坐标约定必须保持一致。
- 现有颜色、法线、高程、夜光和卫星贴图；导入时重新检查色彩空间、压缩格式、mipmap 与许可证清单。
- 当前相机、中心锁定、标签追焦、双层尺度和时间控制的产品规则。

## 必须重做的部分

- Three.js 场景和 WebGL Shader：重写为 UE Material / Material Function；土星环粒子适合 Niagara（太阳日珥已从网页端删除，可在 UE 中用 Niagara 重新实现）。
- HTML/CSS 液态玻璃 UI 与 DOM 标签：重写为 UMG 或 CommonUI；世界标签用 Widget Component，并保持远距隐藏与遮挡规则。
- OrbitControls：改为 Enhanced Input + 自定义 Pawn/PlayerController，明确左键平移、右键环绕、滚轮无级缩放和锁定解除逻辑。
- 浏览器的像素空间标签避让与面板安全区：在 UMG 中重新实现并做 DPI/分辨率测试。

## 大尺度与精度架构

1. 物理层始终保存米、秒、千克和双精度状态，不把渲染压缩坐标写回物理状态。
2. 利用 UE5 Large World Coordinates，同时仍采用相机附近原点/分层尺度；太阳系概览和行星近景使用不同展示变换。
3. 近景切换期间通过遮罩或连续过渡切换尺度，避免单个 UE World 同时承受天文距离与地表厘米细节。
4. 卫星轨道和行星轨道使用程序样条/线材质，按相机距离淡出；不要把轨道烘焙为固定网格。

## 建议实施阶段

1. **冻结契约（1 周）**：锁定天体数据结构、坐标系、UTC/TDB 约定、相机交互和自动测试快照。
2. **UE C++ 骨架（1–2 周）**：导入 C 内核，完成太阳、地球、月球的状态更新和双精度坐标验证。
3. **尺度与相机（2 周）**：实现概览/近景双层、中心锁定、无级缩放与安全边界。
4. **材质与特效（3–5 周）**：迁移地球材质、大气、城市夜光、太阳、气态行星、星环和卫星；性能目标优先于逐像素复刻 Web 版本。
5. **UI 与验收（2–3 周）**：CommonUI/UMG、多级天体树、信息面板、时间轴、手柄/触屏适配和 JPL 固定时刻回归。

单人熟悉 UE 的情况下，达到当前 Web 阶段的功能完整度约需 **8–13 周**；两名开发者并行做物理/场景与材质/UI，可压到约 **5–8 周**。这是工程估算，不含高精度地表漫游、影视级资产制作或主机平台认证。

## 主要风险

- 大尺度精度和尺度切换最容易产生抖动、裁剪与阴影问题，必须先做技术样机。
- GLSL 视觉逻辑不能一键转换为 UE 材质；动态云、大气和太阳需要重新调参。
- 纹理许可证和 NASA/JPL 署名要跟随打包产物，不应只留在开发文档。
- UE 体积、构建时间和显卡要求会明显高于网页版本；如果主要目标是教学网页和快速分享，当前 Web 技术栈仍更合适。
